# 0002 · 文本驱动匹配，不做站点选择器映射

## 状态

已采纳（v1.0.0）

## 背景

两个目标站点（thunderstore.io、www.nexusmods.com）都是 React 单页应用，CSS 类名是编译期哈希（`css-1x2y3z`、`sc-bdVaJa`），每次发版都变。可选的匹配策略有两种：

1. **结构驱动**：为每个页面维护一份 CSS/属性选择器映射表，`querySelector` 拿节点再写译文
2. **文本驱动**：遍历文本节点与白名单属性，拿归一化后的**文本本身**去查词条

## 决策

文本驱动为唯一主路径；结构性兜底只用于「跳过哪些子树」（UGC 忽略区域），不用于「翻译哪个节点」。

## 理由

- 两站的类名与 DOM 结构随发版变化，选择器映射表平均几周就要修一次；文本匹配只受文案变化影响，而站点文案远比类名稳定
- 词条天生按原文组织，文本驱动让「加词条」= 「加一行字典」，不需要理解 DOM
- 命中即写回、译文不再命中词条，扫描天然幂等，MutationObserver 不会自激
- 代价可控：文案改了只漏翻该条，不会像选择器失效那样整块不翻

## 代价

- 精确匹配，站点改文案（哪怕加个句号）就漏翻；靠 `npm run coverage` 与站点的 `collect-ui-text.js` 快照把缺口照出来
- 无法处理「同一个词在不同上下文要不同译法」，除非拆页型分组（本项目按页型分组来缓解）
- 长句（模组描述）天然不匹配，这既是限制也是 UGC 防护的一部分
